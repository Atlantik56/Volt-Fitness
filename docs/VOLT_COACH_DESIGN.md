# VOLT Coach — локальный детерминированный тренер

Статус: реализовано (Sprint 4, advice Sprint 3 сохранены).

## Sprint 4: единое решение CoachDecision

`buildCoachResult` возвращает `{ summary, decision, advice }`. `decision` — одно локальное,
чистое и детерминированное решение: `proceed`, `reduce`, `replace`, `rest` или `complete`.
Оно содержит уникальный приоритет действия, стабильный `reasonCode`, заголовок, объяснение и
отображаемый вариант нагрузки. Предложение не изменяет исходный план.

Порядок принятия решения:

1. `ready=false` — `decision=null`, advice пуст.
2. План отсутствует — `decision=null`; Coach не придумывает тренировку.
3. Совпавшая по нормализованным названию и типу запись сегодняшнего плана — `complete`.
4. Боль `>=7` — `rest`.
5. Боль `5–6` — силовая заменяется существующим восстановлением, кардио/восстановление
   сокращаются, отдых остаётся отдыхом.
6. Низкая готовность по доступным `energy`, `sleepHours`, предыдущим `painAfter` и `effort` —
   `reduce` или, после выраженной боли на силовой, `replace`.
7. Средняя готовность — `reduce`; хорошая — `proceed` без прогрессии.

Внутри Coach типы нормализуются как `strength`, `cardio`, `recovery`, `rest`. Плавание относится
к `cardio`; восстановление и отдых не проваливаются в `strength`. Это локальная модель Coach,
а не новая публичная модель тренировок.

Advice Sprint 3 фильтруются итоговым решением: `complete` не предлагает повтор, `rest` убирает
нагрузочные советы, `replace` не предлагает исходную тренировку, `reduce` показывает конкретное
облегчение, `proceed` оставляет текущий план без прогрессии.

VOLT Coach формирует **не более трёх** рекомендаций на сегодня из уже сохранённых данных.
Он работает без обращений к внешним AI-сервисам и остаётся доступным при отсутствии
Gemini API, ключа, интернета или свободного лимита.

## Граница между Gemini Food Scanner и Coach

В VOLT уже действует интеграция с Gemini (`app/api/food-photo/route.ts`): распознавание еды
по фотографии и чеков. Эта интеграция — часть **питания**, а не Coach, и Sprint 3 её не меняет.

Ключевой факт архитектуры, на котором держится всё разделение:

> `/api/food-photo` возвращает результат **только клиенту** (текст в textarea + заметка).
> В базу он не пишет ничего. Запись появляется лишь после того, как пользователь просмотрел
> результат и отправил форму (`action:"food"`), где сервер заново разбирает текст `parseFood()`
> и сохраняет числа в `food_logs`.

Отсюда следует, что **сохранённая запись питания = подтверждённая запись**. Неподтверждённый или
ошибочный результат распознавания живёт только в состоянии клиентской формы и физически не может
попасть в Coach — тот читает исключительно сохранённые данные.

```
Gemini API
→ распознаёт еду и чеки
→ пользователь проверяет и сохраняет
→ food_logs (подтверждённые числа)

Локальный VOLT Coach
→ читает сохранённые данные
→ применяет детерминированные правила
→ выдаёт рекомендации без внешнего AI API
```

Дополнительные ограничения Coach:

- Coach **не отправляет** фотографии, чеки и записи питания в Gemini повторно.
- Coach использует только **числовые** поля питания (калории, Б/Ж/У, количество блюд).
  Свободный текст `food_logs.note` — это заметка, сгенерированная Gemini; она **не является фактом**
  и в правилах не участвует.
- Сбой, отсутствие ключа или лимита Gemini не влияет на Coach: он не вызывает этот путь вовсе.
- Отсутствие распознанной еды **не означает отсутствие питания** — питание можно вносить вручную.
  Поэтому «нет записей» трактуется как «нет данных», а не как «съедено 0».

## Источники данных

Всё берётся из уже существующего ответа `GET /api/fitness` — новых эндпоинтов не добавляется.

| Источник | Поля | Смысл для Coach |
|---|---|---|
| `wellnessLogs` | `energy` 1–5, `pain` 0–10, `painArea` | самочувствие; строка есть только если пользователь заполнил форму |
| `activity` | `sleepHours`, `steps`, `activeMinutes`, `calories`, `beers` | сон и активность за день |
| `foodLogs` | `calories`, `protein`, `fat`, `carbs`, `items` | подтверждённое питание |
| `workouts` | `date`, `type`, `title`, `effort`, `painAfter` | факт выполнения и боль после прошлой тренировки |
| `measurements` | `date`, `weight` | динамика веса |
| `profile` | `targetWeight`, `startWeight` | цель |
| план дня | `buildHomeWeek()` + `scheduleOverrides` | тренировка, назначенная на сегодня |

Целевые показатели совпадают с теми, что уже отображает интерфейс: 1700 ккал, 150 г белка,
10 000 шагов, 75 минут активности.

## «Данных нет» против «значение равно нулю»

Требование строгое, поэтому в `CoachSummary` все измеримые величины имеют тип `number | null`:

- `null` — данных нет, правило, которому они нужны, **не срабатывает**;
- `0` — реальный ноль, правило срабатывать может.

Конкретные решения:

- **Питание.** Нет записей за сегодня → `logged:false`, калории/белок `null`. Это «ещё не записано»,
  а не «съедено 0». Coach предлагает записать приём пищи, но не делает выводов о дефиците.
- **Активность.** Нет строки `daily_activity` за сегодня → `steps`/`activeMinutes` `null`.
  Строка есть и `steps:0` → это настоящий ноль.
- **Сон.** `sleepHours:0` трактуется как **отсутствие данных**, а не как «спал 0 часов»: форма
  активности сохраняет все поля разом, поэтому незаполненный сон приходит нулём. Та же семантика
  уже используется в `lib/readiness.ts`.
- **Самочувствие.** Нет строки `wellness_logs` за сегодня → `energy`/`pain` `null`, правила по
  энергии и боли не срабатывают, вместо них может сработать подсказка «оцени самочувствие».

## Структура `CoachSummary`

Промежуточная нормализованная сводка — единственный вход для правил.
Строится чистой функцией `buildCoachSummary()`.

```ts
type CoachSummary = {
  date: string;
  sleepHours: number | null;
  energy: number | null;          // 1–5
  pain: number | null;            // 0–10
  painArea: string;
  recentPainDays: number;         // дней с болью ≥ 5 за последние 7
  hasWellness: boolean;
  plan: { title: string; type: string } | null;
  isRestDay: boolean;
  workoutDone: boolean;
  lastWorkoutPain: number | null;
  nutrition: {
    logged: boolean;              // есть подтверждённые записи за сегодня
    meals: number;
    calories: number | null;
    protein: number | null;
    fat: number | null;
    carbs: number | null;
  };
  steps: number | null;
  activeMinutes: number | null;
  weight: {
    current: number;
    previous: number | null;      // предыдущий замер
    baseline: number | null;      // замер ≥14 дней назад
    deltaSincePrevious: number | null;
    deltaSinceBaseline: number | null;
  } | null;
  targets: { calories; protein; steps; activeMinutes; targetWeight };
};
```

## Структура результата

```ts
type CoachAdvice = {
  id: string;                     // стабильный идентификатор правила
  category: "safety" | "escalation" | "recovery" | "training"
          | "load" | "nutrition" | "activity" | "support";
  priority: number;               // уникален; целая часть — уровень P0..P5
  tone: "stop" | "warn" | "good" | "info";
  title: string;                  // действие
  reason: string;                 // почему — обязателен у каждого совета
};

type CoachResult = {
  summary: CoachSummary;
  advice: CoachAdvice[];          // не более 3
};
```

Каждый совет обязан содержать причину (`reason`) — это требование, а не украшение:
рекомендация без объяснения в VOLT не показывается.

## Правила и приоритеты

```
P0 — боль и безопасность
P1 — восстановление
P2 — тренировка
P3 — питание
P4 — активность
P5 — поддержка
```

Приоритет каждого правила **уникален**, поэтому порядок вывода задан явно и не зависит от
порядка объявления правил в коде. Целая часть соответствует уровню P0–P5, дробная —
явный порядок внутри уровня.

| Приоритет | Категория | Правило | Условие |
|---|---|---|---|
| 0 | safety | `pain-high` — заменить нагрузку на щадящий день | `pain ≥ 5` |
| 0.5 | escalation | `pain-persistent` — показаться врачу | `pain ≥ 8` **или** боль ≥ 5 в 3+ днях за последние 7 |
| 1 | recovery | `sleep-short` — снизить объём, приоритет сну | `sleepHours < 6` |
| 1.1 | recovery | `energy-low` — облегчить сессию | `energy ≤ 2` |
| 2 | training | `workout-todo` — выполнить тренировку дня | план есть, не выполнен, `pain < 5` |
| 2.1 | training | `rest-day` — лёгкое восстановление | сегодня день отдыха |
| 2.5 | load | `workout-no-progression` — не повышать веса | `lastWorkoutPain ≥ 3` и `pain < 5` |
| 3 | nutrition | `food-unlogged` — записать приём пищи | нет подтверждённых записей |
| 3.1 | nutrition | `calories-too-low` — добавить еды | `calories < 1200` при наличии записей |
| 3.2 | nutrition | `protein-low` — добрать белок | `protein < 70 %` цели |
| 4 | activity | `steps-low` — добавить шагов | `steps` известны и `< 50 %` цели |
| 5 | support | `weight-fluctuation` — вес вырос временно | вес вырос к прошлому замеру, но тренд за 14 дней вниз |
| 5.1 | support | `wellness-missing` — оценить самочувствие | нет записи самочувствия |
| 5.2 | support | `keep-going` — поддержка | тренировка дня выполнена |

Две категории существуют именно для того, чтобы совет не терялся при дедупликации:

- **`escalation`** отделена от `safety`: направление к врачу дополняет совет «сегодня без нагрузки»,
  а не дублирует его, поэтому они показываются вместе.
- **`load`** отделена от `training`: предупреждение «не повышай веса» должно доходить одновременно
  с общим «выполни тренировку».

Медицинские диагнозы, назначение лекарств и экстремальные ограничения запрещены.
`pain-persistent` не ставит диагноз — он лишь предлагает обратиться к врачу, как это уже
делает существующий блок Readiness.

## Разрешение конфликтов

Применяется после сбора всех сработавших правил, до отсечения по количеству:

0. **Пока данные не загружены — советов нет.** Если `ready === false` (ответ `/api/fitness` ещё не
   получен или запрос завершился ошибкой), `buildCoachResult` возвращает пустой список. Пустое
   начальное состояние экрана неотличимо от «ничего не сделано», поэтому любые утверждения о
   тренировке, питании и самочувствии в этот момент были бы ложными. Проверка вынесена в чистую
   функцию, а не в компонент, и поэтому покрыта тестами.
1. **Безопасность подавляет нагрузку.** При `pain ≥ 5` удаляются все советы, предполагающие
   тренировочную нагрузку: `workout-todo`, `steps-low` и `workout-no-progression`. Последний
   включён сюда потому, что при отказе от нагрузки совет «не повышай веса» противоречил бы
   основному. Совет P0 сам содержит безопасную замену, поэтому пустоты не остаётся.
2. **Выполненная тренировка не предлагается повторно.** При `workoutDone` удаляется `workout-todo`.
3. **Одна категория — один совет.** Из каждой категории остаётся правило с наивысшим приоритетом.
   Категории `escalation` и `load` выделены отдельно именно затем, чтобы важные советы не
   вытеснялись соседними по смыслу (см. таблицу выше).
4. **Сортировка и отсечение.** Приоритеты уникальны, поэтому сортировка по приоритету задаёт полный
   детерминированный порядок без неявных tie-break; список обрезается до трёх.

Правила намеренно не противоречат друг другу по смыслу: «снизить объём» (P1) и «не повышать веса»
(2.5) сочетаются, а «выполнить тренировку» исключается при боли на шаге 1.

## Обработка отсутствующих данных

- Правило, которому не хватает данных, не срабатывает — Coach **не выдумывает показатели**.
- При полном отсутствии данных сработают `wellness-missing`, `food-unlogged` и `keep-going`:
  Coach остаётся полезным и не показывает пустую карточку.
- Ни одно правило не выводит число, которого нет в источнике.

## Интеграция с экраном «Сегодня»

- Компактная карточка `VOLT Coach` на вкладке «Сегодня», сразу под блоком Readiness.
- До получения ответа `/api/fitness` (и при ошибке запроса) карточка показывает нейтральное
  состояние «Собираю данные дня…» и не выдаёт ни одного утверждения. Флаг передаётся пропом
  `ready`, источник истины — состояние `loaded` на экране «Сегодня».
- UI **только отображает** готовый результат: вся логика в `lib/coach.ts`, в компоненте нет
  вычислений, запросов и побочных эффектов.
- Стиль и мобильная адаптивность наследуются от существующих карточек (`card`, токен `--lime`,
  брейкпоинт 760px).
- Данные берутся из уже загруженного `data` — дополнительных запросов не выполняется.

## Архитектура модулей

```
lib/coach.ts            чистые функции: типы, buildCoachSummary, правила, разрешение конфликтов
app/coach-card.tsx      презентационный компонент карточки (без логики)
app/fitness-features.css стили карточки
tests/coach.test.ts     сценарные тесты правил
```

`lib/coach.ts` не импортирует React, не обращается к API и не имеет побочных эффектов —
это делает его полностью тестируемым и детерминированным.

## Риски и тестирование

| Риск | Смягчение |
|---|---|
| Coach выдаст совет по неподтверждённым данным | читаются только сохранённые записи; свободный текст Gemini не используется |
| Ноль спутан с отсутствием данных | все величины `number \| null`, тесты на оба случая |
| Противоречивые советы | шаг разрешения конфликтов + тест на несколько конфликтующих условий |
| Опасный совет при боли | `pain ≥ 5` подавляет нагрузку, отдельный тест |
| Сбой Gemini ломает Coach | Coach не вызывает Gemini; тест на сценарий без Gemini |
| Недетерминированность | чистые функции, отсутствие `Date.now()` внутри правил — дата передаётся аргументом |

Покрытые сценарии: нормальный день, отсутствие данных, отсутствие Gemini API, ошибка распознавания
еды, неподтверждённый результат сканирования, подтверждённое питание, низкий белок, слишком низкая
калорийность, сон менее 6 часов, низкая энергия, боль ≥ 5, выполненная тренировка, несколько
конфликтующих условий, временное увеличение веса.
