# Sprint AI-4 и AI-6 — Insight Layer

Статус: техническое задание. Раздел AI-4 выполнять после вечернего чек-ина.
Раздел AI-6 — только после Memory и накопления данных.

## Цель

Подключить существующие локальные анализаторы к одному контракту и реестру,
сохранив их доменную логику. Затем на этой основе добавить небольшой
проверяемый набор кросс-доменных связей.

Не создавать отдельный Observation Engine: факты уже считают существующие
чистые функции. Не создавать универсальный Recommendation Engine:
`CoachDecision` и progression имеют отдельные safety-инварианты.

Перемещение существующих экспортов не должно ломать потребителей: использовать
временные re-export при необходимости.

## Единый контракт

```ts
type CoachInsight = {
  id: string;
  category: string;
  kind: "observation" | "pattern" | "milestone";
  title: string;
  summary: string;
  confidence: number;       // 0..1, вычислен локально
  evidenceCount: number;
  evidenceHash: string;
  periodStart?: string;
  periodEnd?: string;
  usedSignals: string[];
  suggestionKey?: string;   // ключ локального следующего шага
};
```

Если существующий UI требует `tone` или `priority`, добавить их явно, не
подменять confidence приоритетом.

## Стабильность id и evidence

- `id` описывает смысл правила, а не текущие числа.
- `evidenceHash` строится из нормализованной доказательной базы и версии
  алгоритма, не из текста LLM.
- Порядок входных строк не меняет hash.
- Изменение формулировки без изменения данных не создаёт «новый» инсайт.
- Изменение алгоритма должно иметь явную revision.

## Honesty gate

Каждый анализатор объявляет:

- минимальное число наблюдений;
- минимальный размер каждой сравниваемой группы;
- минимальную дельту;
- окно периода;
- способ вычисления confidence.

Общий helper может проверять контракт, но пороги остаются доменными. Пустые
данные возвращают отсутствие инсайта или typed limited-data result, не
`NaN` и не уверенный текст.

## AI-4 — консолидация

### Порядок

1. Зафиксировать существующие результаты тестами до перемещения.
2. Ввести тип и registry.
3. Подключить `coach-insights`, evening и mood через адаптеры.
4. Вынести только доказанно общие `honesty`/bucket-примитивы.
5. Перевести главную, «Вечерний прогресс», «Мою историю» и API (если он
   остаётся) на общий список.
6. Выбрать судьбу `GET /api/coach/insights`: использовать как единую серверную
   точку либо удалить как мёртвый route отдельным зафиксированным решением.
7. Сохранить существующие пользовательские тексты, если смысл не меняется.

### Не входит

- Новые корреляции.
- Таблица Memory.
- Унификация `CoachDecision`/progression.
- LLM-вызовы.
- Новые экраны.

### Критерии готовности AI-4

- Один публичный registry возвращает все текущие категории.
- Старые анализаторы не запускаются параллельно мимо registry.
- Все инсайты имеют id, evidence, confidence и usedSignals.
- Недостаток данных обрабатывается одинаково по форме, но с доменными порогами.
- UI/API не дублируют расчёт одного инсайта.
- Полные автоматические проверки проходят.

## AI-6 — кросс-доменная аналитика

Реализовать не более 3–4 первых анализаторов после подтверждения размера
реальной выборки. Кандидаты:

- сон ↔ выполнение/субъективная тяжесть тренировки;
- тренировка ↔ время первого напитка/количество алкоголя;
- ужин ↔ количество алкоголя;
- тренировка ↔ настроение;
- вода ↔ самочувствие;
- боль ↔ качество/завершение тренировки;
- этап программы ↔ вес и регулярность.

Для каждого до кода записать гипотезу, поля, исключения, минимальную выборку и
порог эффекта. Фраза должна описывать связь: «в твоих данных в тренировочные
дни первый напиток чаще бывает позже», а не причинность: «тренировки заставляют
тебя пить позже».

## Confidence

На AI-4 не вводить ложную статистическую точность. Допустима простая
документированная шкала, зависящая от:

- размера выборки;
- баланса групп;
- повторяемости направления эффекта;
- величины эффекта относительно порога;
- доли пропусков.

UI может показывать «данных мало / есть признаки / устойчивая закономерность»
вместо процентов. Внутреннее число должно быть воспроизводимым.

## Suggestion

Insight Layer может вернуть один `suggestionKey`, но не генерирует длинный
совет. Registry выбирает максимум один следующий шаг по прозрачному приоритету:
сначала safety, затем восстановление, затем поддерживаемая данными привычка.
Если безопасного полезного шага нет, рекомендация отсутствует.

## LLM

LLM получает только отфильтрованные Memory-слоем структуры:

- summary;
- агрегированные evidence;
- confidence label;
- один suggestion key;
- разрешённый тон.

Модель не получает сырые массивы и не выбирает «самую сильную» корреляцию.

## Тесты

- Контракт и registry: стабильный порядок, дедупликация id.
- Каждый адаптированный старый анализатор сохраняет прежнее поведение.
- Пустые/частичные/несортированные данные.
- Порог `N-1`, `N`, `N+1` для каждого honesty gate.
- Evidence hash стабилен к порядку и меняется при существенном evidence.
- Нет причинных фраз в локальных шаблонах.
- AI-6: fixtures с положительной, отрицательной и отсутствующей связью.
- UI получает не более заданного числа выводов и один suggestion.

## Запреты

- Не строить причинные модели.
- Не запускать LLM внутри анализатора.
- Не добавлять embeddings/vector DB.
- Не создавать общую формулу, скрывающую доменные пороги.
- Не начинать Memory в AI-4.

## AI-4 — что реализовано фактически (2026-07-29)

Структура — не полный набор из раздела "Целевая структура" выше, а минимально
достаточная для критериев готовности:

```text
lib/insights/
  types.ts      # контракт Insight (tone/priority добавлены явно для CoachCard)
  hash.ts       # hashEvidence (djb2, детерминированный) + confidenceFromCount
  registry.ts   # адаптеры + три функции показа
```

`honesty.ts`/`bucket-compare.ts`/отдельные `weight.ts`/`training.ts`/`evening.ts`/
`mood.ts` не выделялись — при таком объёме правил (7 в coach-insights + 4 evening +
2 mood) отдельный файл на каждый источник не окупался; вся логика адаптеров
уместилась в `registry.ts`.

### Три точки показа вместо одного списка

Registry сознательно не сводит всё к одному массиву с одним лимитом:

- `buildCardInsights` — карточка "Что заметил VOLT" на главной. Ровно то же
  поведение, что раньше `buildCoachInsights` (те же id/tone/priority/порядок/
  `COACH_INSIGHTS_MAX`), просто обёрнутое в контракт — нулевой риск для
  существующего UX карточки.
- `buildEveningInsights` — вкладка "Аналитика" вечернего прогресса, полный список
  найденных вечерних паттернов (не капается).
- `buildMoodInsights` — "Что заметил VOLT" в "Моя история" → "Состояние и заметки".

Все три читают одни и те же чистые функции (`buildCoachInsights`,
`findEveningPatterns`, `findMoodPatterns`) — они остались единственным местом
расчёта, registry их не дублирует, только оборачивает.

### id для evening/mood паттернов

`findEveningPatterns`/`findMoodPatterns` возвращают фиксированные (не
интерполированные) строки-константы. Стабильный `id` получен явным
сопоставлением "текст → id" (например `evening-training-later-drink`), а не
парсингом текста. Для непредвиденной новой строки есть честный fallback —
`evidenceHash` от самого текста, чтобы не упасть, а не молчаливо потерять
инсайт.

### Confidence и evidence

Простая документированная шкала (`confidenceFromCount` в `lib/insights/hash.ts`):
`count / (count + minRequired)`, округлено до 0.01. `minRequired` — тот же
порядок величины, что и honesty-порог соответствующего домена (не
пересчитывается заново из внутренностей coach-insights.ts/evening.ts/mood.ts, а
берётся из входных данных на том же уровне детализации, который реально
доступен снаружи). Для evening-паттернов это единый консервативный минимум `3`
(наименьший из порогов внутри `findEveningPatterns`), а не по порогу на каждое
правило — упрощение, задокументированное здесь.

**Исправлено на финальном ревью (2026-07-29):** `evidenceCount` для части
coach-insights id изначально считал числа, не относящиеся к самому
утверждению, и завышал confidence:
- `new-strength-record` считал ВСЕ строки `strengthLogs` (по всем упражнениям),
  а не только по конкретному упражнению из рекорда — рекорд по одному
  упражнению с 2 записями выглядел уверенным просто потому, что в базе много
  записей по другим упражнениям. Исправлено: фильтр по `exercise` (парсится из
  `title`, формат которого фиксирован в `coach-insights.ts`).
- `workouts-missed` считал общее число сохранённых тренировок за всё время —
  не имеет отношения к утверждению "тренировок не было N дней", которое
  целиком опирается на одну дату последней тренировки. Исправлено: `count`
  зафиксирован в `1`.
- `protein-low-week`/`activity-rhythm-up`/`plan-completion-*` считали строки
  входных данных, а не различные дни — несколько записей за один день
  (например несколько приёмов пищи) задваивали evidence. Исправлено:
  `distinctDaysWithin` считает уникальные даты в окне, как и honesty-gate
  внутри самого `coach-insights.ts`.

Также добавлена структурная дедупликация по `id` (`dedupeById`) во всех трёх
экспортируемых функциях registry — раньше уникальность id была свойством
текущих источников данных, а не гарантией самого registry.

### Решение по GET /api/coach/insights

Route не имеет ни одного вызывающего кода в репозитории (проверено grep по
всему проекту) — по факту мёртвый. Решение по разделу "Порядок" п.6: должен был
быть удалён. Удаление файла оказалось заблокировано инструментами сессии
(agent sandbox отклонил `rm`), поэтому вместо удаления route переведён на
`buildCardInsights` — тот же расчёт, что и на главной, без отдельного
дублирующего пути. Если это когда-нибудь понадобится починить руками — можно
просто удалить `app/api/coach/insights/`.

### Что не сделано / риски

- Ручная UI-проверка в браузере (desktop + мобильная ширина) не выполнена в
  этом прогоне: dev-стенд требует пароль, авто-режим сессии заблокировал сброс
  auth-таблиц в dev-БД как деструктивную операцию. `npm test`/`typecheck`/
  `lint`/`build` пройдены и зелёные, но это не заменяет визуальную проверку.
- `evidenceCount` для части coach-insights id (например `new-strength-record`,
  `plan-completion-*`) — честный, но грубый счётчик (общее число записей в
  соответствующем окне), а не точное воспроизведение внутреннего порога
  правила. Это осознанное упрощение уровня AI-4, не путать с полной
  калибровкой confidence (не в скоупе спринта).
