# Спринты AI-12…AI-16 — Адаптивная прогрессия

Статус: план, не начат. AI-1…AI-11 закрыты; это новая продуктовая область.
Предпосылка всей серии — данные из Garmin через intervals.icu
(см. [`GARMIN_BRIDGE.md`](GARMIN_BRIDGE.md)).

## Цель серии

План тренировок адаптируется сам — по выгрузкам с часов и по одной отметке
самочувствия — во всех трёх дисциплинах: зал, бассейн, вело. Пользователь не
подтверждает очевидное; он отменяет то, с чем не согласен.

## Общие ограничения

Из [`AI_PRINCIPLES.md`](AI_PRINCIPLES.md), правятся только отдельным
архитектурным решением:

- LLM **не меняет план и фактические данные**. План меняет детерминированный
  код; консилиум объясняет принятое решение.
- Открытие страницы не вызывает платный запрос; скрытые фоновые вызовы
  моделей запрещены.
- Медицинские выводы запрещены: ВСР и сон — контекст нагрузки, не диагноз.
- Один тяжёлый день не называется провалом.

Продуктовое правило серии: **цифры не перебивают самочувствие.** Плохой сон по
данным при нормальной отметке энергии не режет план молча.

## AI-13 — Объективные сигналы восстановления

Цель: готовность считается по измеренному сну и ВСР, не ломая текущую логику.

- Таблица `daily_health`: `date` UNIQUE, `sleep_seconds`, `sleep_score`,
  `hrv_rmssd`, `resting_hr`, `source`.
- Забор wellness из intervals.icu по диапазону дат.
- [`lib/readiness.ts`](../lib/readiness.ts): источник `sleepHours` —
  измеренный сон, откат на самоотчёт при отсутствии данных. **Формула и веса
  не меняются**: энергия остаётся равной сну по весу, `pain >= 5` остаётся
  жёстким стопом.
- ВСР и пульс покоя — **ограничитель**, а не слагаемое: выраженное отклонение
  от личной базовой линии блокирует рост нагрузки, но само по себе не снижает
  план.

**DoD**
- [ ] При наличии данных сон в готовности берётся с часов.
- [ ] При отсутствии данных поведение не меняется.
- [ ] Тест на конфликт «плохой сон + нормальная энергия»: план не режется.
- [ ] Базовая линия ВСР не строится при недостатке истории; отказ явный.

## AI-14a — Единый план для трёх дисциплин

Цель: цикл плана — единственный источник истины по датам, неделям и
перезапуску. Дисциплина поставляет содержание недели, а не собственную шкалу
времени.

Требование владельца: **план общий для зала, бассейна и вело.** Перезапуск
обнуляет цикл сразу для всех трёх.

Что сейчас нарушает это (проверено на копии боевой базы):

1. **Два якоря дат.** `profile.swim_plan_started_at` живёт отдельно от старта
   цикла. `restartTrainingPlanV3` сбрасывает `training_plan_v3_started_at`, а
   плавательный якорь оставляет — и Foundation продолжает свой отсчёт.
2. **Три нумерации недель.** Общий план считает свою неделю, Foundation —
   1–8, Endurance продолжает сквозным 9–24. Только что начатая Endurance
   показывает «Неделя 9 из 24» при нуле выполненных.
3. **Свой календарь у плавания.** `assignSwimCalendar` назначает даты сам,
   из-за чего слот плана и календарь программы расходятся (см. фикс
   «resolve swim day by program calendar»: план звал w7d3, программа уже
   отдала её на другую дату).
4. **Непоследовательный учёт выполненного.** Endurance ограничивает
   выполнения текущим циклом (`cycleId`, `includeUnscoped`), Foundation
   считает всю историю. У Cycling программы нет вовсе.

Направление работ:

- Единый якорь: дата старта активного цикла для всех дисциплин;
  `swim_plan_started_at` перестаёт быть независимой точкой отсчёта.
- Единая нумерация: неделя цикла. Внутренние индексы определений программ
  остаются деталью реализации и наружу не показываются.
- `restartTrainingPlanV3` переякоривает все дисциплины разом.
- Учёт выполненного везде ограничивается текущим циклом — механизм уже есть
  в Endurance, распространяется на остальные.

**Перезапуск ничего не удаляет.** Выполненные тренировки остаются историей и
в аналитике; они лишь не засчитываются в новый цикл. Миграции аддитивные.

### Найденное препятствие: plan_key не знает о цикле

Ограничение выполнений циклом работает через `plan_key`, но у Foundation он
идентификатора цикла **не содержит**: `buildSwimSnapshot` вшивает `cycleId`
только при наличии `programIdentity` из реестра программ, а у Foundation его
нет. Поэтому перезапуск перестаёт засчитывать лишь старые записи под
legacy-ключами, а выполнения под текущим ключом переживают его.

Полное обнуление требует, чтобы цикл попадал в ключ у всех дисциплин. Это
изменение схемы сопоставления выполненного, поэтому делать его нужно отдельно
и аккуратно: неверный ключ осиротит историю. Ограничение зафиксировано тестом
`tests/plan-restart-all-disciplines.test.ts`.

**DoD**
- [x] Перезапуск переякоривает плавание: единый якорь дат на все дисциплины.
- [x] Ограничение выполнений циклом применяется ко всем программам, а не
      только к endurance.
- [x] Выполненные ранее тренировки остаются в истории и аналитике.
- [ ] `plan_key` содержит идентификатор цикла у всех дисциплин — без этого
      перезапуск не обнуляет счёт полностью.
- [ ] Перезапуск плана возвращает бассейн и вело в начало вместе с залом.
- [ ] Ни один экран не показывает неделю, которой нет в общем плане.
- [ ] Выполненные ранее тренировки остаются в истории и аналитике.
- [ ] Слот плана и календарь дисциплины не могут разойтись по дате.

Спринт предшествует AI-15: строить прогрессию по трём дисциплинам поверх трёх
несогласованных шкал времени бессмысленно.

## AI-14 — Контракт движка прогрессии

Цель: движок перестаёт быть привязанным к залу, поведение зала не меняется.

Обобщить [`lib/progression-engine.ts`](../lib/progression-engine.ts) с
«упражнение → вес/повторы» до контракта, независимого от дисциплины: на входе
история в единицах дисциплины плюс общие сигналы восстановления, на выходе —
прежнее `ProgressionProposal` с кодом причины и `usedSignals`.

Существующие правила зала (`pain-deload`, `two-easy-increase`,
`two-hard-decrease`) становятся первой реализацией контракта.

Общий слой поверх всех дисциплин: низкая готовность или отклонение ВСР
**запрещают рост**, не трогая текущую нагрузку. Одно правило на три
дисциплины, а не три копии.

**DoD**
- [ ] Существующие тесты зала проходят без изменений.
- [ ] Ограничитель восстановления покрыт отдельными тестами.
- [ ] `progression_decisions` хранит дисциплину; миграция аддитивная.

## AI-15 — Вело и бассейн

Цель: прогрессия работает во всех трёх дисциплинах.

**Вело.** Единицы: средняя и нормализованная мощность, время в зонах.
Прогрессия по длительности и целевой зоне, оценка FTP по заездам. Модуль
Cycling уже есть, мощность приходит с трейнера готовой.

**Бассейн.** Единицы: дистанция, темп на 100 м, SWOLF. Правило, которого нет
в зале: **ухудшение SWOLF при росте темпа означает распад техники — объём не
наращивается.** Программа Foundation остаётся канонической, адаптация ложится
поверх неё, как гибкая неделя поверх программы.

Порядок внутри спринта решается при старте: у вело данные проще, у бассейна
втрое больше сессий в неделю, то есть быстрее накопится история.

**DoD**
- [ ] Предложение строится на реальных импортированных данных, не на
      синтетике.
- [ ] Отказ при недостатке данных явный (`limitedData`), а не выдуманный.
- [ ] Контракт дизайна VOLT Swim не нарушен
      ([`design/VOLT_SWIM.md`](design/VOLT_SWIM.md)).

## AI-16 — Автоматизация и объяснения

Цель: убрать подтверждения очевидного и объяснять решения.

**Автоматизация.** Связать существующую уверенность с существующими
решениями: сопоставление `high` (score ≥ 0.75) привязывается и подтверждается
само, `medium` и `low` по-прежнему спрашивают. Уверенное предложение
прогрессии применяется само, `limitedData` — нет.

Принцип: не «спросить и ждать», а **сделать и дать откатить** — строка вида
«сон 4:20, снизил объём на круг» с кнопкой «я в порядке, верни». Ручной ввод
остаётся ровно один: отметка самочувствия, с подстановкой того, что уже есть
в данных.

**Объяснения.** Консилиум разворачивает готовое решение в разбор «почему так,
а не иначе»: код отдаёт действие, код причины и `usedSignals`, модели делают
из этого текст. Триггер — явный запрос, не открытие страницы. Расхождение
цифр и ощущений проговаривается прямо. Формулировки — по
[`AI_10_CONSTRUCTIVE_FEEDBACK.md`](AI_10_CONSTRUCTIVE_FEEDBACK.md).

**DoD**
- [ ] Типовая тренировка доходит от часов до истории без единого тапа.
- [ ] Любое автоматическое действие видно и отменяемо; отмена восстанавливает
      прежнее состояние.
- [ ] Объяснение опирается только на переданные факты и не изобретает причин.
- [ ] При недоступности провайдеров решение и краткое объяснение остаются
      (Lite Coach работает без внешнего API).
