# Правила для AI-агентов

Эти правила дополняют корневые `AGENTS.md` и `CLAUDE.md`. Канонические документы
и утверждённые изображения имеют приоритет над визуальной импровизацией.

## Правила для Claude Code

1. До редактирования назвать ограниченный scope и ожидаемые файлы.
2. Прочитать корневой `CLAUDE.md`, этот документ и минимальный набор из раздела
   «Экономия контекста» ниже.
3. Не загружать весь каталог дизайн-системы и весь репозиторий по умолчанию.
4. Для VOLT Swim обязательно прочитать `docs/volt-swim/SPRINTS.md`,
   `docs/design/VOLT_SWIM.md` и открыть эталон нужного экрана.
5. В отчёте перечислить использованные design docs, визуальную проверку и ограничения.

## Правила для Codex

1. Следовать корневому `AGENTS.md`; исследовать task-specific paths первыми.
2. До реализации сверить screen spec, нужные component specs и только затем код.
3. Делать минимальный связный diff без попутного редизайна и новых абстракций.
4. Для VOLT Swim обязательно прочитать `docs/volt-swim/SPRINTS.md`,
   `docs/design/VOLT_SWIM.md` и открыть эталон нужного экрана.
5. Проверить diff, релевантные тесты и визуальные состояния; не push/deploy без запроса.

## Что запрещено менять

Без явного запроса пользователя запрещено менять:

- бизнес-логику, API, модели данных, маршруты и существующее поведение;
- утверждённую композицию, визуальный язык, navigation и роль hero;
- семантическую палитру, типографические роли, spacing, radius, depth и motion tokens;
- эталонные изображения, их имена, кадрирование и статус утверждения;
- границы модулей и продуктовую роль VOLT Coach;
- несвязанные экраны, архитектуру, schema и пользовательские данные.

## Экономия контекста: читать только нужное

| Задача | Обязательный минимальный набор |
|---|---|
| Цвет/стекло | `02-colors.md`, `05-glass-system.md`, нужный screen spec |
| Layout/типографика | `03-typography.md`, `04-spacing.md`, нужный screen spec |
| Компонент | один файл из `components/`, нужный screen spec |
| Motion | `06-motion.md`, нужный component/screen spec |
| Обычный экран | его файл из `screens/` + только затронутые foundations/components |
| Swim UI | `screens/swim.md`, `docs/design/VOLT_SWIM.md`, `docs/volt-swim/SPRINTS.md`, эталон экрана + затронутые component docs |

`README.md` используется как router. Не читать все screen specs и все компоненты
«на всякий случай». Если задача меняет общий токен или navigation, расширить
контекст только на реально затронутые потребители.

## Утверждённые концепции

Не изменять, не «улучшать» и не осовременивать утверждённую концепцию без явного
запроса пользователя. Если требования конфликтуют с эталоном, описать конфликт
и запросить выбор. Отсутствие концепта означает сохранить текущий язык и оставить
предложение на утверждение, а не самостоятельно объявить новый вариант эталоном.

Для обычного VOLT общий background reference указан в `README.md` и
`05-glass-system.md`. Использовать его для понимания среды, overlay и глубины,
но не считать заменой утверждённого screen mockup.

## Design Compliance Audit

После реализации или изменения любого экрана агент обязан до объявления задачи
завершённой провести self-audit по официальной дизайн-документации.

Обязательные источники проверки:

- [`01-design-principles.md`](../01-design-principles.md);
- [`05-glass-system.md`](../05-glass-system.md);
- [App Background Architecture](../01-design-principles.md#app-background-architecture);
- [Motion System](../06-motion.md);
- утверждённый mockup экрана (PNG/Figma), указанный в его screen spec или
  [индексе эталонных экранов](../README.md#индекс-утверждённых-экранов-volt-20).

Для каждого источника в итоговом отчёте явно указать один статус с кратким
объяснением:

- `✅ Complies` — требование соблюдено;
- `❌ Does not comply` — требование не соблюдено.

Если нарушено хотя бы одно правило дизайна, задача не завершена. Агент обязан
продолжать итерации до соблюдения всех документированных требований либо указать
конкретный конфликт, для разрешения которого необходимо решение пользователя.
