# Sprint AI-5 — Coach Memory

Статус: техническое задание. Начинать после единого Insight Layer.

## Цель

VOLT должен помнить, какие детерминированные инсайты уже показаны, скрыты или
обновлены. Memory управляет повторным показом, но не хранит скрытые рассуждения
LLM и не подменяет историю фактических данных.

## Ожидаемые точки изменения

- `lib/db.ts` — аддитивная миграция
- новый `lib/insight-memory.ts` или `lib/insights/memory.ts`
- `lib/insights/registry.ts`
- места показа инсайтов в `app/`
- API actions для shown/dismiss при необходимости
- новые unit- и service/integration tests

## Минимальная модель

Предпочтительная таблица:

```text
insight_log
- id
- insight_id
- evidence_hash
- source_revision
- first_shown_at
- last_shown_at
- dismissed_at
- resolved_at
- show_count
```

Уточнить типы и naming по conventions SQLite проекта. Нужны уникальность или
индекс, позволяющие быстро найти состояние пары
`insight_id + evidence_hash`. Если приложение когда-либо станет
мультипользовательским, схема должна допускать `profile_id`, но AI-5 не
переводит весь проект на multitenancy.

## Семантика

- `first_shown_at` — первый фактический показ пользователю.
- `last_shown_at` — последний фактический показ.
- `dismissed_at` — пользователь явно скрыл текущую версию.
- `resolved_at` — паттерн перестал быть актуальным или цель достигнута.
- `show_count` — число фактических показов, не вычислений в фоне.
- `source_revision` — версия анализатора.
- `evidence_hash` — версия доказательной базы из Insight Layer.

Memory не записывает chain-of-thought, prompt, полный LLM-ответ или
эмоциональную интерпретацию пользователя.

## Публичные операции

```text
shouldShowInsight(insight, memory, now)
markInsightShown(insight, now)
dismissInsight(insightId, evidenceHash, now)
resolveInsight(insightId, evidenceHash, now)
```

Операции идемпотентны. Рендер страницы без фактической видимости карточки не
должен искусственно увеличивать `show_count`; выбрать и зафиксировать
практичный критерий «показано».

## Правила показа

- Новый `insight_id` показывается.
- Тот же id и тот же evidence hash не повторяется ежедневно.
- Тот же id с существенно новым evidence hash может быть показан как
  обновление после cooldown.
- Dismiss подавляет конкретную evidence-версию.
- Новая evidence-версия после dismiss не показывается немедленно из-за
  минимального шума; правило cooldown фиксируется тестом.
- Resolved не возвращается без нового evidence/revision.
- Safety-инсайты не могут быть навсегда скрыты обычным dismiss; их отдельное
  поведение должно быть явно согласовано с существующим CoachDecision.

Точные интервалы не придумывать внутри реализации: сначала предложить значения
и получить продуктовый выбор либо использовать явно документированные
консервативные defaults с конфигурацией.

## Обновлённый инсайт

Если эффект изменился, UI должен различать повтор и обновление:

```text
Раньше: в тренировочные дни первый напиток был позже на 45 минут.
Сейчас: разница выросла до 95 минут на новой выборке.
```

Числа готовит локальный анализатор. LLM при необходимости только формулирует
готовую дельту.

## Миграция и отказоустойчивость

- Новая таблица не меняет старые данные.
- При пустой Memory система ведёт себя как первый запуск.
- Ошибка записи shown не должна ломать страницу или скрывать safety advice.
- Повтор API-запроса не создаёт дубли.
- Миграция проходит на существующей production-like копии SQLite.
- Не очищать журнал автоматически в AI-5; политика retention — отдельное
  решение после оценки размера.

## Не входит

- Долговременная память разговора.
- Векторный поиск, embeddings и semantic memory.
- Автоматическая запись «характера пользователя».
- Milestones.
- Изменение алгоритмов инсайтов.
- Общая event-sourcing архитектура приложения.

## Тесты

- Первый показ.
- Повтор с тем же hash.
- Новый hash и cooldown.
- Dismiss и новый evidence.
- Resolve и повторное появление.
- Смена source revision.
- Идемпотентный `markInsightShown`.
- Конкурентные/повторные запросы не увеличивают count дважды.
- Ошибка БД даёт безопасный fallback.
- Safety-поведение отдельно.
- Миграция со старой схемы и пустой журнал.

## Критерии готовности

- Одинаковая карточка не повторяется при каждом открытии.
- Существенно обновившийся вывод может вернуться как обновление.
- Пользователь может скрыть несрочный инсайт.
- Память не содержит raw notes, prompts и chain-of-thought.
- LLM не решает, показывать ли инсайт.
- Полные проверки проходят; ручной сценарий refresh/navigation проверен.
- Решения cooldown и safety записаны в `ROADMAP_AI.md`.

## Запреты

- Не использовать conversation history как Memory инсайтов.
- Не хранить скрытые выводы модели.
- Не добавлять глобальный cache, который может скрыть новый safety advice.
- Не начинать Milestones в этом спринте.

## AI-5 — что реализовано фактически (2026-07-29)

### Модель и файлы

```text
lib/insights/memory.ts        — чистые операции (shouldShowInsight/markInsightShown/
                                 dismissInsight/resolveInsight), константы cooldown
lib/insight-memory-store.ts   — DB-слой поверх insight_log (upsert, auto-resolve)
lib/db.ts                     — миграция v12 (insight_log + индексы)
app/api/insights/route.ts     — GET (surface=card|evening|mood, фильтрует + отмечает
                                 показ) и POST (action:"dismiss")
app/use-insight-surface.ts    — клиентский хук: fetch на mount + dismiss
```

`lib/insights/registry.ts` не тронут в части бизнес-логики — добавлено только
поле `sourceRevision` в контракт `Insight` (нужно Memory, чтобы отличать смену
алгоритма от нового evidence).

### Правила показа и cooldown (итоговые значения — см. также ROADMAP_AI.md AI-5)

`COOLDOWN_DAYS=7`, `DISMISS_COOLDOWN_DAYS=7`, `SAFETY_DISMISS_COOLDOWN_DAYS=1`,
`SAFETY_INSIGHT_IDS=∅` — все константы в `lib/insights/memory.ts`, с обоснованием
в комментариях. Состояние переходов реализовано как явный `ShowDecisionKind`
(`new/repeat/update/suppressed-repeat/suppressed-dismissed/suppressed-resolved`),
не просто `boolean` — это же используется, чтобы отличить "повтор" от
"обновления" на будущее (текст "было/стало" из раздела "Обновлённый инсайт" в
эту реализацию не добавлен — вне минимального scope AI-5, хук уже есть через
`kind`).

### Критерий "показано" — архитектурное решение

Insight Layer (AI-4) вычислялся полностью на клиенте поверх уже загруженного
`data`. Поскольку Memory обязана трогать SQLite (недоступно в браузере),
вычисление + фильтрация переехали на сервер: `GET /api/insights?surface=...`
сам является "фактическим показом" — вызывается клиентским хуком
(`app/use-insight-surface.ts`) ровно при монтировании реальной поверхности
(её компонент до этого не был смонтирован — переход на вкладку/раздел), не на
каждый ре-рендер. Это не мелкая деталь, а изменение модели данных AI-4:
`app/page.tsx`/`app/coach-card.tsx`/`app/evening-progress.tsx`/`app/mood-section.tsx`
больше не вызывают `buildCardInsights`/`buildEveningInsights`/`buildMoodInsights`
напрямую на клиенте для отображения — они остались только внутри
`app/api/insights/route.ts` (и в тестах).

### Дедупликация фактического показа

`SHOWN_DEDUP_WINDOW_SECONDS=5` — повторные вызовы `markInsightShown` в течение
этого окна (двойной эффект React StrictMode в dev, сетевой ретрай) считаются
ОДНИМ показом, `show_count` не растёт дважды. На уровне БД конкурентная запись
защищена уникальным индексом `(insight_id, evidence_hash)` через
`INSERT ... ON CONFLICT DO UPDATE` — параллельные запросы не создают дублирующих
строк.

### Отказоустойчивость

`GET`/`POST /api/insights` оборачивают вызовы Memory в `try/catch`: при ошибке
БД отдаётся НЕОТФИЛЬТРОВАННЫЙ список кандидатов (может показать что-то
повторно, но никогда не даёт пустой экран и не прячет всё из-за бага в
journal-слое). Это единственное место, где "честный повтор" предпочтён "тишине".

### Что не сделано / риски

- Текстовое "было X → стало Y" для обновлённого инсайта (раздел "Обновлённый
  инсайт" в спеке) не реализовано — `kind:"update"` уже размечает такие случаи,
  текст дельты можно добавить в UI отдельным, более мелким изменением.
- Retention insight_log не настроен (осознанно — отдельное решение по спеке).
- Домашний CTA-тизер вечернего прогресса (`summarizeEveningToday` в
  `app/evening-progress.tsx`) продолжает читать `buildEveningInsights` напрямую
  (без Memory) — он выбирает только между двумя общими подписями ("есть
  новый вывод"/"посмотреть изменения"), не показывает содержание инсайта,
  поэтому не может утечь скрытый/dismissed факт; но теоретически может
  предложить открыть вкладку, где Memory что-то уже скроет. Задокументированный,
  принятый компромисс, не исправлялся в рамках минимального scope.
