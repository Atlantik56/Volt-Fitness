# Roadmap AI-спринтов VOLT

Статус: текущий план. Начальная точка: `main` после внедрения «Вечернего
прогресса» и «Моей истории» 28 июля 2026 года.

Этот roadmap заменяет прежнюю спринтовую очередь для AI-развития. Исторические
Sprint 1–8 остаются в `VOLT_ROADMAP.md`, но не должны выполняться параллельно с
AI-1…AI-6 без отдельного решения пользователя.

## AI-1 — стабилизация аналитики

### Цель

Убрать подтверждённые расхождения до появления общего Insight Layer и Memory.
Спринт не меняет пользовательский функционал.

### Scope

- Создать `lib/stats.ts`; унифицировать `avg`, `round1`, `daysBetween`.
- Явно определить поведение пустых массивов и некорректных дат.
- Заменить дубли только в подтверждённых потребителях:
  `lib/coach.ts`, `lib/coach-insights.ts`, `lib/coach-weekly.ts`,
  `lib/evening.ts`, `lib/mood.ts`, `lib/progression-engine.ts`,
  `app/progress-model.ts`, `app/exercise-progress.ts`.
- Вынести общий `weightStep`, если обе реализации действительно семантически
  одинаковы; иначе задокументировать отличие.
- Провести инвентаризацию трёх источников подсказок прогрессии:
  `lib/progression-engine.ts`, `app/exercise-progress.ts`,
  `StrengthAdvice` в `app/fitness-features.tsx`.
- Выбрать канонический источник правил и убрать противоречивые советы, не
  объединяя разные UX-моменты искусственно.

### Не входит

- Новый UI, миграции БД, новые инсайты.
- Изменение safety-порогов без отдельного продуктового решения.
- Repo-wide cleanup утилит и типов.
- Переименование существующих движков.

### Критерии готовности

- Общие функции имеют документированный контракт и unit-тесты, включая пустой
  ввод, один элемент, дробные значения и границы дат.
- В затронутых файлах нет локальных копий с тем же смыслом.
- Подсказки прогрессии не противоречат подтверждаемому предложению.
- Существующие snapshots/тексты меняются только при исправлении
  подтверждённого расхождения.
- Полный test/typecheck/lint/build проходит.

**Контракт статистических примитивов (`lib/stats.ts`):**

- `avg([])` → `null` (не `NaN`). `avg([x])` → `x`.
- `round1(n)` — округление до одного знака, `-0` нормализуется в `0`
  (устраняет реальный баг: без нормализации `coach.ts` мог показать «+-0 кг»
  для малой отрицательной дельты веса).
- `daysBetween(from, to)` — целые сутки между датами `"YYYY-MM-DD"`, всегда
  через `T00:00:00Z`; одинаковые даты → `0`; некорректная дата → `null`, не
  `NaN`. Не зависит от `Date.now()`, локали или текущей таймзоны.

**Подтверждённое расхождение:** `avg([])` в `lib/evening.ts` возвращала `NaN`
(0/0), а в `lib/coach-weekly.ts` — `null`. Устранено переходом на общий
контракт; ни один существующий вызов не полагался на `NaN`-поведение (все
обёрнуты в `.length` проверки или уже ожидали `null`).

**`weightStep`:** реализации в `lib/progression-engine.ts` и
`app/exercise-progress.ts` были побайтово идентичны (одинаковый порог `<=0`,
одинаковый паттерн для гантелей, одинаковые значения 1/2.5 кг). Объединены:
каноническая функция — в `lib/progression-engine.ts`, `app/exercise-progress.ts`
переиспользует её через re-export.

**Три источника подсказок прогрессии:**

1. `lib/progression-engine.ts` (`buildExerciseProgression`) — **канонический**
   источник подтверждаемого изменения нагрузки. Работает после завершения
   тренировки, использует историю прошлых сессий, `painAfter`, `coachAction`,
   `workoutComplete`, `targetMaxReps`. Требует **двух подряд** «Легко»/«Тяжело»
   для increase/decrease; deload — только при тяжёлой боли.
2. `app/exercise-progress.ts` (`progressionDecision`) — live-подсказка
   на следующий подход прямо во время тренировки, использует последнюю
   зафиксированную запись (в т.ч. текущую, ещё не сохранённую). Более
   консервативных подтверждений не ждёт, но и не идёт против направления
   канонического решения — оставлен как самостоятельный UX-момент, как
   разрешено ТЗ («живая подсказка» ≠ «подтверждаемое решение»).
3. `app/fitness-features.tsx` (`StrengthAdvice`) — прежде содержала третий,
   независимый набор правил (числовая формула `+1 кг` без учёта `weightStep`,
   срабатывающая после одной лёгкой тренировки вместо двух). Это было
   единственное подтверждённое противоречие по направлению/числу. Исправлено:
   компонент больше не предлагает конкретное число, только нейтрально
   описывает факт и ссылается на решение VOLT Coach.

Прямого противоречия по направлению (одна сторона — increase, другая —
decrease/deload для одних и тех же сигналов) между источниками 1 и 2 не
обнаружено и зафиксировано тестами `tests/progression-consistency.test.ts`.

**Результаты проверок:** `npm test` — 212/212 passed; `npm run typecheck` —

## AI-2 — единый Context Builder

### Результат AI-2

Выполнено 28 июля 2026 года. Все критерии готовности выполнены.

**Подтверждённые проблемы (аудит):**

  (окно 7 дней) фактически всегда был `0` в обоих каналах — реальный баг того

- Этап программы определялся только статичным `app/personal-data.ts`

- Три места независимо копировали похожий SQL: `app/api/coach-chat/route.ts`,

**Изменённые файлы:**

- `lib/ai-context-data.ts` (новый) — единый серверный загрузчик
  `loadAiCoachContextData(db, options)` и типы слоя `AiCoachContextData`
  (profile, measurements, foodLogs, workouts, wellnessLogs, activity,
  moodLogs, personalRecords, programStages, lastPhotoDate); там же —
  `selectActiveProgramStage(stages, date)` и `loadPersonalRecords(db, date, limit)`.
- `lib/ai-context.ts` — `buildAiCoachContext` теперь принимает
  `AiCoachContextData` (обратно совместимо с прежним `CoachInput`-подобным
  входом, все новые поля опциональны); добавлены `AiCoachContext.wellness`,
  `.wellnessNote`, `.programStage`, `.personalRecords`, `.lastPhotoDate`,
  `mood.latest.note`; `renderAiCoachContextText` дополнен строками по этим
  полям без удаления существующих строк.
- `app/api/coach-chat/route.ts`, `mcp-server.ts`,
  `app/api/progression/route.ts` («explain») — ручные SQL-выборки заменены на
  вызов `loadAiCoachContextData`.
- `tests/ai-context-data.test.ts` (новый) — 22 теста загрузчика и контекста.

**Единый загрузчик и потребители:** `loadAiCoachContextData(db, {date, plan?,
historyDays?, historyRowsLimit?, workoutsLimit?, personalRecordsLimit?})` —
единственное место, где для AI-потребителей выполняется SQL.
`app/api/coach-chat/route.ts` и `mcp-server.ts` вызывают его с настройками по
умолчанию и отличаются только `plan` (chat передаёт реальный план дня, MCP —
всегда `null`). `app/api/progression/route.ts` («explain») вызывает тот же
загрузчик с `historyDays:0, workoutsLimit:0, personalRecordsLimit:0` —
различие каналов выражено через `options`, а не через отдельный загрузчик или
свой SQL. Три представления разделены: `AiCoachContextData` (сырые/ограниченные
строки из SQLite) → `AiCoachContext` (нормализованный локальный объект, без
UI/API-зависимостей, пригоден для Coach/MCP/будущих отчётов) →
`renderAiCoachContextText` (компактная LLM-проекция).

**Семантика `historyDays` (исправлено после независимого ревью):**
`historyDays` — это календарное окно в ДНЯХ, а не число строк. Загрузчик
вычисляет начало окна как `date − (historyDays − 1)` дней (UTC-полночь, без
зависимости от `Date.now()`/локали/таймзоны — тот же принцип, что
`lib/stats.ts daysBetween`) и фильтрует `measurements`/`foodLogs`/
`wellnessLogs`/`activity`/`moodLogs` через `date>=cutoff AND date<=anchor`, а
не через `LIMIT`. Несколько записей за один день (например, три приёма пищи)
не сокращают охваченный период — лимит по числу строк (`historyRowsLimit`,
по умолчанию 1000) — это отдельный safety-cap НА СЛУЧАЙ патологического
объёма внутри уже вычисленного календарного окна, а не подмена окна. Значение
`historyDays: 0` явно отключает все пять исторических массивов (пустые `[]`),
а не «окно в 0 дней, включающее сегодня». При некорректной anchor-дате
(`Date.parse` даёт `NaN`) `calendarWindowStart` не бросает исключение —
вырождает окно в один день вместо падения загрузчика.

**Личные рекорды (исправлено после независимого ревью):** раньше
`personalRecords` строились функцией `computeStrengthRecords` над последними
300 строк `strength_logs`, из-за чего старый настоящий рекорд мог потеряться
за более новыми записями с меньшим весом. Теперь `loadPersonalRecords(db,
date, limit)` — агрегированный SQL-запрос (CTE `MAX(weight) GROUP BY
exercise` + подзапрос на самую раннюю дату достижения этого веса) по ВСЕЙ
истории `strength_logs` до анкорной даты, без загрузки сырых строк в JS.
`isRecord` — `true`, если по упражнению больше одной записи. Поле
`strengthLogs`/тип `StrengthLogRow` из `AiCoachContextData` удалены за
ненадобностью — рекорды приходят уже агрегированными от загрузчика (что и
требовалось изначальным ТЗ: «личные рекорды или необходимые агрегаты»).

**Структурное отделение пользовательского текста (усилено после независимого
ревью):** `wellness_logs.note` и `mood_logs.note` добавлены в
`AiCoachContext.wellnessNote`/`mood.latest.note` — отсутствие заметки или
пустая строка → `null`. Нормализация вычищает C0/C1 control-символы (не
только `\s` — включая, например, ANSI escape-последовательности), схлопывает
пробелы/переносы строк и ограничивает 300 символами (защита в глубину поверх
лимита в `app/api/fitness/route.ts`). В LLM-проекции заметка больше не
оборачивается только в кавычки (кавычки внутри самого текста заметки могли бы
визуально «закрыть» цитату раньше времени) — используется явный блок
`renderUserDataBlock` с ограждением из символа `§§§`, который перед вставкой
нейтрализуется внутри самого текста заметки (`§` → `'`), поэтому пользователь
не может подделать закрывающий маркер изнутри своих данных. Тест
подтверждает только структурное отделение и нормализацию (ровно один
настоящий закрывающий маркер, ни одного управляющего символа из заметки в
проекции) — тест НЕ утверждает, что prompt injection невозможно выполнить:
LLM всё равно читает текст внутри блока, просто граница «где данные
заканчиваются» не зависит от их содержимого. Промпт (`SYSTEM_PROMPT` в
`lib/ai-coach.ts`) не менялся.

**`program_stages` и fallback:** приоритет — фактическая запись
`program_stages`, покрывающая дату (`start_date<=date` и `end_date is null
или >=date`); статичный план (`app/personal-data.ts`) — fallback для дат до
первой записи, в «зазорах» между этапами и когда записей нет вовсе.
Пересечения (несколько записей покрывают одну дату — таблица не защищена
уникальным ограничением, только валидацией формы) разрешаются
детерминированным тай-брейком: более поздняя `start_date`, при равенстве —
больший `id`. Источник отражён в `AiCoachContext.programStage.source`
(`"program_stage"` или `"static_plan"`). Миграция БД не потребовалась.

Проверка дат (усилена после независимого ревью): `isValidIsoDate` больше не
просто сверяет строку с regex `YYYY-MM-DD` — проверяет реальную календарную
дату через `Date.UTC(y, m, 0).getUTCDate()` (число дней в месяце с учётом
високосных лет), отбрасывая невозможные месяц/день (`"2026-13-01"`,
`"2026-02-30"`). Если сама anchor-дата, переданная в `selectActiveProgramStage`,
невалидна как календарная дата — функция сразу возвращает `null`, не
сравнивая её строково со `start_date`/`end_date` записей (иначе, например,
`"2026-02-30"` лексикографически прошла бы сравнение с валидной `start_date`).
Записи `program_stages` с невалидной `start_date`/`end_date` тоже отбрасываются
и не участвуют в выборе.

**Ограничения LLM-проекции:** только последние 5 тренировок, до 5 личных
рекордов (по всей истории, не по ограниченному окну), только сегодняшняя
заметка самочувствия и только последняя заметка настроения (не вся история
заметок), фото — только дата без имени файла и пути, `coach_conversation` в
контекст не попадает вовсе (отдельный канал в `app/api/coach-chat/route.ts`),
`settings`/API-ключи в загрузчике не запрашиваются вообще. Тест на плотном
fixture (30 дней данных по всем категориям) фиксирует измеримый лимит: рендер
< 8000 символов.

**Тесты (`tests/ai-context-data.test.ts`, 22 шт.):** chat/MCP получают
идентичные данные при одинаковых опциях; `wellness_logs.note`/`mood_logs.note`
присутствуют и безопасно размечены структурным блоком; управляющие символы и
попытка подделать закрывающий маркер не разрушают границу блока (без
утверждения о невозможности injection); отсутствие wellness-записи и заметки
— `null`, не `""`; реальный ноль (`pain:0`, `calories:0`) отличается от
отсутствия записи; `historyDays` — календарное окно, несколько записей в один
день не сокращают период; `historyDays:0` явно отключает исторические
массивы; старый личный рекорд не теряется за 300+ новыми записями меньшего
веса; фактический `program_stage` приоритетнее статичного плана; зазор между
этапами и отсутствие записей — fallback; пересекающиеся этапы —
детерминированный выбор; запись с несуществующим месяцем/днём и невалидная
anchor-дата не выбирают этап по строковому сравнению; високосный год

- Порог выборки фиксируется до реализации каждого анализатора.

### Scope

- Ограниченный набор кросс-доменных анализаторов из `INSIGHT_ENGINE.md`.
- Автоматические и ручные Milestones из `MILESTONES.md`.
- Отображение истории в «Моей истории» без перегрузки главного экрана.

### Критерии готовности

- Ни один текст не превращает корреляцию в причинность.
- Каждый вывод показывает/хранит evidence count и confidence.
- Слабые выборки дают честное пустое состояние.
- Milestones идемпотентны и не дублируются после пересчёта.
- LLM получает только готовые агрегаты.
- Полные проверки и ручная desktop/mobile QA проходят.

### Фактическое решение (2026-07-29): кросс-доменные анализаторы отложены

Аудит реальной production-БД (только агрегаты — количество записей/период/пропуски,
без raw notes/фото) показал: приложение работает ~9 дней, и по всем 7 кандидатам
из `INSIGHT_ENGINE.md` данных либо нет вовсе, либо выборка на порядок меньше
любого честного минимума:

| Кандидат | Реальные данные на момент аудита | Вердикт |
|---|---|---|
| Сон ↔ тяжесть/выполнение тренировки | 0 записей `sleep_hours/minutes` | нереализуемо |
| Тренировка ↔ первый напиток/алкоголь | 0 `alcohol_logged` | нереализуемо |
| Ужин ↔ алкоголь | 0 `dinner`/`alcohol_logged` | нереализуемо |
| Тренировка ↔ настроение | 6 mood-записей (5 дней) | **уже реализовано в AI-4** (`mood-training-better`), не дублировать |
| Вода ↔ самочувствие | 0 `water_logged` | нереализуемо |
| Боль ↔ качество/завершение тренировки | 1 из 6 workouts с `pain_after>0` | нереализуемо (не с чем сравнивать) |
| Этап программы ↔ вес/регулярность | 0 `program_stages` | нереализуемо |

Решение (согласовано с пользователем): ни один кросс-доменный анализатор в AI-6
не реализован — код анализаторов не написан. Реализована только вторая часть
scope: Milestones + «Моя история». Возврат к анализаторам — отдельный будущий
спринт после накопления данных (в первую очередь sleep/alcohol/dinner/water —
сейчас их вообще нет, независимо от порогов).

### Фактически реализовано (Milestones + «Моя история»)

Первый набор автоматических вех (`lib/milestones.ts`, `MILESTONES_REVISION="ai6-v1"`):
`first-workout`, `workout-count` (10/25/50/100), `personal-record` (вся история
PR, не только последний), `new-min-weight`, `program-stage-completed`,
`best-month-regularity` (honesty gate: только полностью завершённые месяцы,
минимум 4 тренировки в месяце — `BEST_MONTH_MIN_WORKOUTS`), `photo-checkpoint`
(только факт+дата, раз в 30+ дней — `PHOTO_CHECKPOINT_MIN_DAYS`). Восьмой пункт
исходного списка ("устойчивое улучшение показателя") сознательно не дублирован —
это уже существующий weight-trend инсайт из AI-4.

Ручные вехи — новая аддитивная таблица `milestones` (миграция v13, только для
того, что невозможно восстановить из источников: дата/заголовок/заметка/
категория), CRUD через `/api/fitness` (`addMilestone`/`updateMilestone`/
`deleteMilestone`). «Моя история» получила вкладку «Вехи» с группировкой по
месяцам, фильтром по категории и Lite-обзором месяца без LLM/API. Главная
страница показывает не более одной (последней) вехи.

## Общие запреты

- Не начинать следующий спринт автоматически.
- Не пушить и не деплоить без разрешения пользователя.
- Не менять приложение вне scope текущего спринта.
- Не удалять пользовательские данные и старые миграции.
- Не использовать LLM для вычислений, confidence или выбора фактов.
- Не превращать заметки пользователя в диагнозы.
